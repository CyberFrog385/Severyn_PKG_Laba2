# Отчёт по лабораторной работе 2

## Что сделано

Приложение `Laba2` анализирует файлы растровых изображений: определяет формат по сигнатуре, читает метаданные, при необходимости декодирует пиксели и считает статистику. Есть графическое приложение на FLTK и консольный анализатор `Laba2Scan`.

Поддерживаются шесть форматов: BMP, PNG, JPEG, GIF, TIFF, PCX. Все парсеры, декодеры и кодеки написаны с нуля: Deflate (inflate), LZW, PackBits, RLE4/RLE8, дифференциальное кодирование PNG, IDCT и Хаффман JPEG.

## Сборка и запуск

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/Laba2Scan "task/Для проверки Lab2" --deep
./build/Laba2
```

Подробности для Windows и CLion: `help/build-windows.md`.

## Структура проекта

| Каталог | Назначение |
| --- | --- |
| `src/model` | Формат, запись результата, состояние сканирования, вывод в текст и CSV |
| `src/core` | `FileHead` (ленивое чтение диапазонов), определение формата, извлечение метаданных |
| `src/core/parsers` | По одному парсеру на формат: заголовки, поля, предупреждения |
| `src/core/codec` | Декодеры пикселей, кодеки сжатия, анализатор пикселей |
| `src/io` | Обход каталогов и пул потоков |
| `src/controller` | Сканирование, агрегация состояний, сохранение CSV |
| `src/view` | Окно FLTK: таблица результатов, предпросмотр, панель полей, строка состояния |

Библиотека `laba2_core` не зависит от FLTK, поэтому консольный анализатор собирается и запускается без графической части. Приложение `Laba2` — тонкая оболочка над той же библиотекой.

## Архитектурные решения

**Ленивое чтение.** `FileHead` читает только те диапазоны, которые запросил парсер, и объединяет соседние запросы в один. В отчёте видно, сколько байт реально прочитано: на 6.8 МБ файлов из задания читается ровно 6.8 МБ заголовков, а не сами пиксели.

**Потоки.** `DirectoryScanner` обходит дерево каталогов, `ThreadPool` раздаёт файлы рабочим потокам. Число потоков по умолчанию равно числу ядер, его можно задать ключом `--workers`. Сканирование поддерживает отмену и не блокирует интерфейс.

**Разделение проверки и декодирования.** Парсер всегда заполняет метаданные и список замечаний. Глубокий анализ (`--deep`) дополнительно декодирует пиксели и считает число цветов и энтропию, но не может испортить результаты разбора: ошибки декодера попадают в отдельное поле.

**Три состояния проверки.** `OK`, `предупреждение` и `файл повреждён` плюс отдельное состояние «не изображение» для файлов с чужим расширением и без сигнатуры. Предупреждение не считается ошибкой, но видно пользователю.

**Ограничения ресурсов.** `DecodeLimits` ограничивает число пикселей (64 млн) и объём декодированных и сжатых данных (512 МБ). При превышении декодирование прекращается с пометкой «ограничено», а не падает.

## Поддерживаемые сжатия

| Формат | Методы |
| --- | --- |
| BMP | BI_RGB (1/4/8/16/24/32 бит), RLE4, RLE8, битовые маски каналов |
| PNG | Deflate, все пять типов фильтра, чанки IDAT, interlaced, tRNS |
| JPEG | Baseline и extended sequential (SOF0/SOF1), все частоты дискретизации |
| GIF | LZW, первый кадр, локальные и глобальные палитры |
| TIFF | Полосы, PackBits, LZW, Deflate, предикторы 1 и 2, палитра, 1/8/16 бит |
| PCX | RLE, 1/4/8 бит на палитре и 24 бит RGB |

Прогрессивный JPEG распознаётся, разбираются его заголовки, но пиксели не восстанавливаются: это осознанное ограничение, о котором сообщается явным предупреждением, а не ошибкой.

## Проверка корректности

**Эталонная папка задания.** Все 24 файла из `task/Для проверки Lab2` разбираются без ошибок и предупреждений, включая глубокий анализ. Для каждого извлечены размер, разрешение, глубина цвета, модель цвета, палитра, число использованных цветов и энтропия.

**Сгенерированный корпус.** `tests/data` содержит 80 файлов, покрывающих все шесть форматов и варианты сжатия, включая RLE4/RLE8, delta-escape, tRNS, билевел, 16 бит и TIFF с альфа-каналом. Генераторы лежат в `tests/generate_edge_cases.py` и `tests/generate_tiff_cases.py`; Pillow используется только для создания эталонов, никогда для проверки.

**Повреждённые файлы.** `tests/corrupt` содержит обрезанные файлы, завышенные длины чанков, оборванные RLE-потоки, файл с чужим расширением и не-изображение с расширением изображения. Для каждого ожидается конкретное сообщение на русском языке, а не просто ненулевой код возврата.

**Сравнение с Pillow.** Каждый файл корпуса декодируется собственным кодом и сравнивается с результатом Pillow по всем каналам. 79 из 80 файлов совпадают побайтово. Единственное расхождение — прогрессивный JPEG, который намеренно не декодируется.

Для JPEG допускается расхождение до 16 по модулю на канал: это нормальная погрешность округления в IDCT и преобразованиях цветности. Фактические значения: `jpeg_gray` MAE 0.010, `jpeg_large` MAE 0.251, `jpeg_q50` MAE 0.280, `jpeg_q75` MAE 0.332, `jpeg_q95` MAE 0.231.

**Автоматические тесты.** `ctest` выполняет 7 проверок: разбор папки задания, вывод CSV, строгий прогон корпуса, строгий глубокий прогон корпуса, прогон повреждённых файлов, проверку кода возврата `--strict` и проверку счётчиков в сводке.

## Что было исправлено по ходу работы

Отдельные находки, которые стоит отметить, потому что они нетривиальны:

- **Смещение IFD в TIFF.** Значение `StripOffsets` вычисляется после размещения всех значений каталога; запись значения-заглушки давала сдвиг на несколько байт и полностью нечитаемые файлы.
- **Выравнивание RLE по границе слова.** Отступ считается от абсолютной позиции в потоке, а не от длины блока и не от начала строки. Раньше это ломало вторую и последующие строки изображения.
- **Режим RLE4.** Закодированная команда занимает два байта: счётчик и байт значений, чередование старшей и младшей половин. Однобайтовое прочтение счётчика из старшей половины давало сдвиг на пиксель уже в первой строке.
- **Значения 0, 1 и 2 зарезервированы.** Блок из трёх пикселей в режиме RLE4 пришлось кодировать не как литерал `0, 3`, а как отдельные одиночные прогоны: счётчик 2 означает переход (`delta`), а не два пикселя.
- **Альфа-канал в TIFF.** Тег `ExtraSamples` определяет, является ли четвёртый канал альфой; при его отсутствии 4-канальный TIFF остаётся RGB и не должен выдаваться как RGBA.
- **Счётчик «не изображений».** Он увеличивался только при неудачном открытии файла, но не при неопознанной сигнатуре, поэтому файл с чужим расширением учитывался как обычный.

Отдельно отмечу расхождение с Pillow по RLE4: в режиме абсолютных значений Pillow вычисляет число байт как `счётчик // 2`, из-за чего нечётный счётчик теряет последний пиксель. Собственный декодер проверен по спецификации и по независимой реализации и совпадает с ними; расхождение устранено за счёт того, что генератор не выпускает нечётные счётчики.

## Известные ограничения

- Прогрессивный JPEG не декодируется до пикселей.
- Тайловые TIFF и раздельное хранение плоскостей (PlanarConfiguration = 2) не поддерживаются.
- Цветовая модель YCbCr в TIFF не поддерживается.
- JPEG с фактором дискретизации больше 2 обрабатывается приближённо; корректно покрыты факторы 1 и 2.
- Интерактивное поведение окна FLTK, работа на больших каталогах и отмена сканирования проверялись вручную и не покрыты автоматическими тестами.
