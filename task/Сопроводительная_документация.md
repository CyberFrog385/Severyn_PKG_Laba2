# Сопроводительная документация

**к лабораторной работе № 2 «Анализатор растровых файлов»**

Документ отвечает на два вопроса, обязательных по условию работы: каким способом «доставались» данные об изображении и какими внешними библиотеками пользовались. Дополнительно приведено обоснование соблюдения жёсткого архитектурного ограничения для группы 10А.

## 1. Перечень внешних библиотек

Единственная сторонняя библиотека, используемая в приложении, — **FLTK 1.4.5** (Fast Light Toolkit, исходники vendored в `third_party/fltk-1.4.5`). Она применяется **исключительно для отрисовки графического интерфейса и вывода самого изображения** в окне просмотра. Никаких других внешних библиотек проект не подключает.

Применены следующие компоненты FLTK: окно, кнопки, поля ввода, выпадающий список, флажки, таблица с полосами прокрутки, надпись и поле вывода файла, а также холст для отображения декодированного растра.

**Библиотеки для получения метаданных не использовались.** В частности, в коде отсутствуют любые обращения к Pillow, libpng, libjpeg, stb_image и аналогичным библиотекам распознавания форматов. Проверка по исходным текстам приложения даёт нулевое количество совпадений. Pillow применяется исключительно в скриптах подготовки проверочных файлов `tests/generate_edge_cases.py` и `tests/generate_tiff_cases.py`, то есть вне приложения, только для создания эталонов и не для чтения свойств на стороне программы.

Условие работы для группы 10А допускает внешние библиотеки «только для рендеринга (показа) самой картинки в интерфейсе, но не для чтения ее свойств». Применение FLTK целиком укладывается в это исключение.

## 2. Способ получения данных

Данные об изображении получены единственным способом: файл открывается как поток байтов, после чего из него читаются **конкретные диапазоны по смещениям, известным из заголовков**, а полученные значения интерпретируются вручную в соответствии со спецификациями форматов. Никакой файл целиком не читается и целиком не загружается в память.

Механизм доступа реализован в классе `FileHead` (`src/core/FileHead.h`, `src/core/FileHead.cpp`). Класс открывает файл один раз и предоставляет операцию чтения диапазона по смещению и длине, объединяя соседние запросы в одно системное чтение, чтобы не делать системный вызов на каждый байт. Парсеры форматов не содержат собственной работы с файловой системой и не открывают дескрипторы.

Разбор ведётся двумя способами в зависимости от формата.

**Прямое чтение по смещениям** применяется для BMP, PNG и TIFF, где в заголовке присутствует таблица смещений на данные палитры, полос или чанков. Нужные байты запрашиваются адресно.

**Последовательное чтение со скользящим окном** применяется для GIF и JPEG, где смещения заранее неизвестны: данные идут подряд, и заголовок приходится искать, читая файл вперёд. Для этих форматов реализован класс `ScanWindow` (`src/core/ScanWindow.h`), который читает файл блоками по мере надобности, сдвигает начало окна и отбрасывает уже разобранные байты, а также устанавливает жёсткий предел на суммарный объём прочитанного.

Формат определяется по сигнатуре содержимого файла, а не по расширению, поэтому подменённое расширение обнаруживается корректно.

Все многобайтовые числа читаются через класс `ByteReader` (`src/core/ByteReader.h`), который явно учитывает порядок байтов. Это обязательно для TIFF, где маркер `II` означает little-endian, а `MM` — big-endian; тот же порядок байтов применяется ко всем последующим полям.

Полный перечень извлекаемых характеристик с указанием источника каждой приведён в разделе «Откуда берётся каждая выводимая характеристика» основного отчёта.

## 3. Собственные реализации алгоритмов

Помимо чтения заголовков, для глубокого анализа требуется восстановление самих пикселей. Все кодеки сжатия реализованы вручную, без обращения к сторонним библиотекам:

- **Deflate (inflate)** — для PNG, включая все пять типов предсказания строк: None, Sub, Up, Average и Paeth, а также восстановление значений до 16 бит.
- **LZW** — для PNG и TIFF, с расширением словаря и сбросом кода.
- **PackBits** — для TIFF.
- **RLE4 и RLE8** — для BMP, включая режим абсолютных значений и управляющие коды 0, 1 и 2.
- **Хаффман и обратное дискретное косинусное преобразование (IDCT)** — для JPEG.
- **CRC-32** — для проверки целостности чанков PNG.

## 4. Обоснование соблюдения жёсткого ограничения

Жёсткое условие запрещает использовать сторонние библиотеки для получения метаданных и предписывает открывать файл как поток байтов и самостоятельно читать массивы по спецификации, находя маркеры, сигнатуры и теги.

Соблюдение этого условия обеспечивается архитектурно, а не только декларативно. Вся логика разбора, чтения и декодирования собрана в статической библиотеке `laba2_core`, которая **не зависит от FLTK ни в одной строке кода**. Графическая оболочка подключается только поверх неё.

Это подтверждается следующими проверками:

- В определении цели `laba2_core` перечислены 29 файлов исходного кода, и ни один из них не относится к каталогу `src/view`.
- Поиск включений заголовков FLTK (`<FL/...>`) по каталогам `src/core`, `src/model`, `src/controller` и `src/io` не даёт ни одного совпадения. Заголовки FLTK подключаются только в `src/main.cpp` и в файлах каталога `src/view`.
- Для цели `laba2_core` не задано ни одной зависимости компоновки: в файле сборки отсутствует строка `target_link_libraries` для неё, есть только директория включений.
- Консольный анализатор `Laba2Scan` компонуется только с `laba2_core` и не подключает FLTK вообще. Следовательно, все метаданные в нём извлекаются без участия графической библиотеки.
- Графическое приложение `Laba2` компонуется с `laba2_core` и `fltk::fltk`, при этом FLTK используется только для отрисовки.

Таким образом, метаданные не могут быть получены через FLTK даже случайно: соответствующий код физически отделён и не имеет доступа к графической библиотеке.

## 5. Средства разработки и сборки

| Средство | Назначение |
| --- | --- |
| C++20 | язык реализации |
| FLTK 1.4.5 | графический интерфейс и вывод изображения |
| Стандартная библиотека C++ | файловый ввод-вывод, `std::filesystem`, потоки |
| CMake 4.3.4 | система сборки |
| Ninja | генератор сборки |
| Python 3 с Pillow | подготовка проверочных файлов, вне приложения |

Сторонние библиотеки применяются только в скриптах подготовки тестовых данных. В среде сборки FLTK отключены необязательные компоненты: GL, формы, fluid, а также конфигурации с общей библиотекой и X11 backend на Apple, что сокращает сборку.

## 6. Сборка и проверка

Конфигурация и сборка:

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
```

Консольный анализатор собирается отдельно и не требует графической библиотеки:

```
cmake --build build --target Laba2Scan
```

Автоматическая проверка:

```
ctest --test-dir build --output-on-failure
```

Проверяется корректность разбора папки задания, вывод в CSV, строгий прогон сгенерированного корпуса изображений, строгий глубокий прогон, обработка повреждённых файлов, ненулевой код возврата в строгом режиме и значения счётчиков в сводке.

Запуск консольного анализатора:

```
./build/Laba2Scan "task/Для проверки Lab2" --deep
```

## 7. Ограничения

Прогрессивный JPEG распознаётся по маркеру `SOF2`, его заголовки разбираются, но пиксели не восстанавливаются; выводится предупреждение, а не ошибка, поскольку такой файл корректен. Не поддерживаются тайловые TIFF и раздельное хранение плоскостей — эти случаи выявляются по тегам и сообщаются явным сообщением об ошибке. JPEG с коэффициентом дискретизации больше двух обрабатывается приближённо, методом ближайшего соседа.
